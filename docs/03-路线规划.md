# 路线规划：pstack 的"计划"是三样东西

[docs/00](00-pstack设计地图.md) 说过，pstack 默认不写计划文档。它的路线规划落在三样东西上：一份原样抄来的步骤清单，一个先定下来的数据形状，一串每步都能验证的提交。下面逐个看这次是怎么做的。

## 1. 挑执行手册，把步骤原样抄进待办

这个任务既要做一个 App，又要留下能教学的过程记录，23 本执行手册里没有一本同时覆盖这两件事。按 poteto-mode 的路由规则，"没有合适手册"或者"人要事后审查"的工作，走 [figure-it-out](../.claude/skills/figure-it-out/SKILL.md)。它的作用是给这个任务**现场设计**一本执行手册。

按规定，待办清单第一项是读原则，然后是 Phase A 到 E。这次实际的清单是：

```text
[x] 读 poteto-mode 的 Principles 部分
[x] Phase A 定框架：完成断言、规模、严格程度        → docs/01、docs/02
[x] Phase B 设计流程：拆单元、风险最大的先做、验证先于功能
[x] Phase C 按假设循环执行，每单元验证后再往下
[x] Phase D 决策日志一路记                          → decisions.tsv
[x] Phase E 对照 Phase A 的断言整体验证，把反复出现的纠正写成脚本
[ ] architect（多模型设计草图）  skip: 数据形状小、可撤销，存储键带 v1 版本号可迁移
[ ] 委派子代理写代码              skip: 本次为控制成本在单会话完成，偏离了 Feature 手册，见 README
[ ] interrogate（多模型挑错）     skip: 同上
```

注意最后三行。pstack 要求跳过的步骤**留在清单里**，写上 `skip: 原因`。你检查它的时候，看的就是这些 skip 的理由站不站得住。

## 2. 先定数据形状

poteto-mode 的规定是："写任何代码之前，先说出数据形状，再按 model-the-domain 原则选组织结构。"[architect](../.claude/skills/architect/SKILL.md) 技能更进一步，要求**先写调用方怎么用**，再从用法推出类型。这次先写下的用法是：

```js
let s = emptyState();
s = apply(s, { type: 'add', item: { kind: 'subscription', name: '爱奇艺 VIP', amountCents: 2500, cycle: 'monthly', start: '2026-01-28' } });
summary(s, '2026-09-25');   // { monthlyCents: 8833, fruitDue: 3, nextActivity: {...} }
agenda(s, '2026-09-25');    // [{ date, kind, text, id }]，按日期排好
s = apply(s, { type: 'bought', id, on: '2026-09-25' });
```

从用法推出了三个结构上的决定，每个都对应一条原则：

| 决定 | 原则 | 它避免了什么 |
|---|---|---|
| 三种条目用 `kind` 区分，每种的规则集中在一张 `KINDS` 表里 | [model-the-domain](../.claude/skills/principle-model-the-domain/SKILL.md)："用注册表或查找表代替散落各处的分支" | UI 里到处写 `if (kind === 'subscription')`，加第四种事务时要改好几个文件 |
| 下次扣费日、下次该买日**推算**出来，不存 | [make-operations-idempotent](../.claude/skills/principle-make-operations-idempotent/SKILL.md)：无论之前跑了几次，结果都收敛到同一状态 | 存一个 `nextDate` 每月回写。月末截断会越推越早（1/31、2/28、3/28...），漏一次回写就错 |
| 金额用"分"存整数；表单字符串只在 `app.js` 的 `PARSE` 表里转成合法数据 | [boundary-discipline](../.claude/skills/principle-boundary-discipline/SKILL.md)：在系统边界设防，内部信任类型 | 浮点误差；领域代码里到处检查"金额是不是数字" |

`KINDS` 表长这样（[`app/domain.js`](../app/domain.js)）：

```js
const KINDS = {
  subscription: { monthlyCents: ..., due: (it, today) => nextRenewal(it, today), text: ... },
  purchase:     { monthlyCents: () => 0, due: (it, today) => /* 由 lastBought 和 everyDays 推算 */, text: ... },
  activity:     { monthlyCents: () => 0, due: (it, today) => (it.date >= today ? it.date : null), text: ... },
};
```

日程、汇总卡片、"我去买"消息，都是从这一张表推出来的。

## 3. 吞吐检查点

[Feature 执行手册](../.claude/skills/poteto-mode/playbooks/feature.md) 第 3 步要求写下四项。某一项不适用也不能删，要写 `n/a: 原因`：

- **先阻塞的步骤。** `domain.js` 的数据形状和测试。UI 和端到端测试都依赖它，必须先做。
- **能并行的工作流。** `n/a`：总共约 500 行，UI 依赖领域层，端到端测试依赖 UI 的选择器，拆开并行反而要多次对接。
- **共享可变状态。** `n/a`：只有页面自己写 localStorage，一个写入者。（后来的纠偏发现，恰恰是**缺少**共享状态出了问题，见 docs/04。）
- **最小安全拆分。** 一个人做。理由同上：代码耦合，单一负责人内部再分步骤更安全。

这四项的用处是逼你在动手前想清楚：什么必须先做，什么能同时做，哪里会打架。项目大了，这一步决定开几个子代理、各自用哪个 worktree。

## 4. 提交顺序本身就是论证

[sequence-verifiable-units](../.claude/skills/principle-sequence-verifiable-units/SKILL.md) 要求：每个单元以一个检查结束，绿了才走下一步；提交的顺序要能让审查者"看着它变红，再变绿"。这次的 git 历史就是按这个排的：

```text
a6b5379 chore: vendor pstack skills and agents          脚手架：先把工具放进来
23bd01b prototype: settle layout and date math ...       先解决风险最大的未知数
010b96d test: domain behavior ... (red)                  先写失败的测试
8b4168e fix(test): point node --test at test/*.test.js   发现"红"是假的，修观察方法（见 docs/04 纠正 1）
1bf7871 feat(domain): ...                                测试变绿
52da451 feat(app): family agenda page with verify script 界面 + 唯一裁判
94e04d0 feat(app): share the shopping list ...           纠偏（见 docs/04 纠正 4）
2f1655a fix(app): generate ids without crypto.randomUUID  真环境暴露的问题（见 docs/04 纠正 5）
8830099 fix(app): drop unknown stored kinds on load ...   提交前自己重读代码发现的两处小问题
8a74260 docs: learn pstack through the family agenda build 学习文档
```

用 `git log --reverse -p` 从头读，每个提交都能单独成立，读下来就是一个论证过程。

## 什么时候才真写一份计划

工作跨多个阶段、多个 PR 的时候。用 [multi-phase-plan](../.claude/skills/poteto-mode/playbooks/multi-phase-plan.md) 执行手册。它的计划是一张勾选清单，每个框写明什么证据能勾掉它，而且**只出计划不实现**，等你明确说"开始"。

写完之后用脚本检查计划格式：

```bash
node .claude/skills/poteto-mode/scripts/check-plan.mjs <plan.md>
```

这个脚本本身就是 encode-lessons-in-structure 原则的例子：作者不再用文字提醒"计划里别用长破折号、每个 PR 要有验证块"，而是写成脚本，不合格就报行号。它针对的是 Cursor 云端、多 PR、每个 PR 十条验证通道的大项目，对这次的小项目太重了，所以没用。
